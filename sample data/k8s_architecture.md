# Comprehensive Guide to Kubernetes Architecture and Components

The architecture of a production Kubernetes cluster is split into two primary operational layers: the Control Plane and the Worker Nodes. The Control Plane acts as the central brain of the cluster, maintaining the desired cluster state, making global scheduling decisions, and responding to system events. Worker nodes provide the underlying compute infrastructure, running containerized workloads managed directly by Control Plane components.

## Control Plane Architecture and Core Services

The central entry point of the entire Kubernetes Control Plane is the Kubernetes API Server, known as kube-apiserver. The API Server exposes a RESTful interface operating over HTTPS, typically listening on port 6443. Every internal component within the cluster, as well as external management tools like kubectl, communicates exclusively through the API server. When a request is received, the API server authenticates the client, authorizes the operation, validates the requested YAML or JSON payload, and updates the cluster state stored in etcd. The API Server is stateless and can scale horizontally across multiple master nodes to guarantee high availability.

Persistent state for the entire cluster is maintained inside etcd, a distributed, highly available key-value store. etcd stores the complete configuration and current runtime status of every object in the cluster, ranging from Pods and Services to ConfigMaps and persistent volume bindings. Communication with etcd occurs over default client port 2379 and peer-to-peer port 2380, utilizing the Raft consensus algorithm to achieve strong consistency across all cluster nodes. Because etcd represents the single source of truth for the cluster, loss of etcd quorum renders the control plane incapable of processing cluster state modifications.

Workload assignment is governed by the kube-scheduler daemon. The scheduler continuously monitors etcd via the API Server for newly created Pods that lack a node assignment. Upon detecting an unassigned Pod, the scheduler evaluates all available worker nodes using a two-phase process consisting of filtering and scoring. During filtering, nodes that fail basic hardware requirements, volume mounts, taints, or affinity constraints are eliminated. During scoring, the scheduler ranks the remaining eligible nodes based on resource optimization algorithms to select the optimal destination for the Pod.

System controllers operate continuously inside the kube-controller-manager process to reconcile differences between the actual status of the cluster and its desired state. The controller manager runs multiple specialized control loops, including the Node Controller, which detects node outages; the Replication Controller, which maintains correct Pod counts; and the Endpoints Controller, which populates Service endpoint objects. In cloud environments, the cloud-controller-manager isolates cloud-provider-specific logic, interfacing with cloud infrastructure APIs to manage external load balancers, persistent disks, and IP routing tables.

## Worker Node Architecture and Networking Services

Worker nodes execute containerized workloads under the supervision of local node daemons. The primary management agent running on every worker node is the kubelet. The kubelet Listens on port 10250 and receives Pod Specifications (PodSpecs) directly from the API Server. It communicates with the node's local container runtime through the Container Runtime Interface (CRI) to ensure containers are pulled, launched, and maintained according to their specifications. The kubelet also continuously runs liveness and readiness probes, reporting pod health and node metrics back to the API Server.

Network traffic routing on individual nodes is executed by the kube-proxy daemon. Kube-proxy maintains network rules across nodes using iptables rules or IPVS virtual servers. When a client application attempts to access a Kubernetes Service via its virtual IP address, kube-proxy intercepts the traffic and balances the load across active backend Pods. This mechanism ensures seamless internal service discovery and reliable network routing across dynamic Pod IPs.

The underlying execution of container images relies on lightweight container runtimes such as containerd or CRI-O. These runtimes implement standard Open Container Initiative (OCI) specifications, pulling container images from remote registries, configuring isolated namespaces and cgroups, and mounting root file systems.

Kubernetes enforces a flat cluster networking model where every Pod receives its own unique IP address. Under this model, Pods on any worker node can communicate directly with Pods on any other node without Network Address Translation (NAT). Cluster network plugins (CNIs) like Calico, Flannel, or Cilium enforce this model by dynamically creating virtual interfaces and managing routing tables across all cluster nodes.
