# Troubleshooting Kubernetes Deployments and Error Analysis

## Diagnosing Common Pod Failures

Application deployment failures in Kubernetes generally originate from container image errors, runtime crashes, memory starvation, or resource scheduling constraints. Identifying the root cause requires analyzing Pod status indicators and inspecting container execution logs.

When a Pod displays the ImagePullBackOff or ErrImagePull status, the worker node's kubelet is unable to retrieve the specified container image from the container registry. This issue usually occurs because of typographical errors in the image repository tag, non-existent image paths, missing imagePullSecrets for private image registries, or registry rate-limiting. Inspecting the Events section at the bottom of a `kubectl describe pod` command reveals the exact HTTP error code returned by the remote registry during the image pull attempt.

The CrashLoopBackOff status indicates that a Pod successfully pulled its container image and started execution, but the entrypoint process repeatedly crashed shortly after launch. Kubernetes automatically attempts to restart failing containers using an exponential backoff delay ranging up to five minutes. Common causes of CrashLoopBackOff include unhandled software exceptions, missing environment variables, syntax errors in mounted configuration files, or failed network connections to downstream databases. Developers can troubleshoot runtime crashes by reading historical logs using `kubectl logs <pod-name> --previous`, which prints the stdout and stderr output generated by the container immediately prior to its termination.

When a container exits abruptly with Exit Code 137, the host operating system has forcibly killed the process due to memory exhaustion. This OOMKilled condition occurs when application memory consumption spikes beyond the hard limit configured in the PodSpec. To resolve OOMKilled failures, engineers must examine application memory profilers to fix memory leaks or increase the memory limit allocation defined inside the deployment manifest.

Pods remaining indefinitely in a Pending state indicate that the kube-scheduler cannot locate a worker node capable of satisfying the Pod's placement constraints. This problem frequently stems from cluster-wide CPU or memory exhaustion, unbound PersistentVolumeClaims, or restrictive node taints that lack corresponding tolerations on the Pod. Running `kubectl describe pod` provides explicit event messages explaining why candidate nodes were rejected during the scheduling filter phase.

## Diagnostic Command Workflows and Network Troubleshooting

Effective cluster management relies on targeted diagnostic workflows using the kubectl command-line tool. To view detailed node resource usage across the cluster, administrators run `kubectl top nodes`, which displays real-time CPU and memory metrics collected by the Metrics Server. Similarly, `kubectl top pods` highlights resource-intensive workloads consuming excessive CPU or memory allocations.

When troubleshooting complex multi-tier application failures, network service connectivity issues must be analyzed systematically. A frequent failure pattern involves frontend microservices failing to establish HTTP connections with backend API Services. The diagnostic workflow begins by verifying that the selector labels defined in the Service manifest accurately match the labels applied to the backend target Pods. Running `kubectl get endpoints <service-name>` reveals whether the Service has successfully discovered active backend Pod IP addresses. If the endpoints list returns `<none>`, a label selector mismatch exists between the Service and Pod definitions.

If endpoints are correctly populated but network requests continue to time out, the internal cluster DNS service (CoreDNS) must be inspected. CoreDNS translates Service names into internal virtual IP addresses. Testing DNS resolution involves launching an interactive ephemeral container to run lookup commands such as `nslookup backend-service.default.svc.cluster.local`. If DNS resolution fails, checking CoreDNS health logs with `kubectl logs -n kube-system -l k8s-app=kube-dns` usually identifies upstream DNS forwarding failures or missing network policy permissions blocking UDP port 53 traffic.
